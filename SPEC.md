# Image Codec Compare — техническое задание

Версия 0.1. Документ предназначен для исполнения агентом (Claude Code): содержит контракты
модулей, формулы и критерии приёмки. Всё, что помечено `[v2]`, в первой версии не реализуется,
но архитектура не должна этому мешать.

---

## 1. Цель

Инструмент, который отвечает на один вопрос: **до какого качества я готов сжать свои фотографии.**

Ответ даётся глазами, а не цифрами. Метрики — вспомогательные. Поэтому главный приоритет
интерфейса — быстрый, точный, не отвлекающий просмотр двух вариантов одного кадра при
произвольном увеличении.

### Два режима работы

| | Режим «Кодек» | Режим «Фото» |
|---|---|---|
| Источник | один общий на обе панели | у каждой панели свой |
| Что различается | формат и параметры | сам кадр |
| Настройки кодирования | у каждой панели свои | общие для всех панелей |
| Эталон для метрик | общий оригинал | собственный оригинал каждой панели |
| Типовая задача | «WebP q80 или AVIF q50?» | «какой из двух дублей лучше переживёт сжатие?» |

### Не является целью

- Редактор изображений. Никаких кроп/поворот/коррекций.
- Серверная обработка. Бэкенда нет вообще, файлы не покидают браузер.
- HDR и цвета глубже 8 бит. Осознанно отложено.
- Пакетная обработка папок с выгрузкой. `[v2]`

## 2. Стек и жёсткие ограничения

- **TypeScript, strict.** Vite. Без UI-фреймворка в ядре.
- **Ядро (`core/`, `codecs/`, `metrics/`) не знает о DOM.** Чистые функции и классы, покрытые
  юнит-тестами. UI-слой отделён и может быть заменён.
- Состояние — маленький собственный сторе (observable + подписки), ~100 строк. React не нужен:
  всё тяжёлое рисуется в canvas императивно, реактивности требует только хром интерфейса.
- **Кодеки:** `@jsquash/jpeg | webp | avif | jxl | png | oxipng`, декодирование HEIC —
  `libheif-js`.
- **Заголовки COOP/COEP обязательны** (`Cross-Origin-Opener-Policy: same-origin`,
  `Cross-Origin-Embedder-Policy: require-corp`) — без них не работают wasm-треды и SIMD,
  AVIF и JXL становятся неприемлемо медленными. Настроить в `vite.config.ts` для dev и
  задокументировать для прода в README. Если целевой хостинг не даёт ставить заголовки —
  фолбэк на `coi-serviceworker`.
- Никаких CDN в рантайме: wasm-бинарники собираются в бандл и грузятся лениво.
- Целевые браузеры: последние 2 версии Chrome, Firefox, Safari. Мобильный Safari — обязателен
  и является главным ограничителем по памяти.

### ВАЖНО про API кодеков

Точные имена опций каждого кодека **брать из `.d.ts` установленного пакета**, а не из этого
документа и не по памяти — они менялись между мажорными версиями `@jsquash`. Ниже указано,
какие параметры должны быть доступны пользователю по смыслу; маппинг на реальные поля —
задача реализации. Каждый адаптер обязан иметь тест на round-trip.

## 3. Форматы

### Кодирование (участвуют в сравнении)

| id | Библиотека | Пользовательские параметры |
|---|---|---|
| `original` | — | нет (псевдоформат: отдаём исходные байты и исходные пиксели) |
| `jpeg` | mozjpeg | quality 0–100, progressive, субдискретизация 4:4:4 / 4:2:0 |
| `webp` | libwebp | quality 0–100, lossless, near-lossless, effort/method 0–6 |
| `avif` | libavif | quality 0–100, effort/speed, субдискретизация 4:4:4 / 4:2:0 |
| `jxl` | libjxl | quality 0–100 (маппится в distance), effort 1–9, lossless, progressive |
| `png` | oxipng | уровень оптимизации 0–6 (всегда lossless) |

`png` включён не как конкурент, а как контроль: на нём PSNR обязан быть `Infinity`. Если это
не так — сломан пайплайн, а не кодек.

Для WebP при lossless обязательно выставлять флаг `exact`, иначе теряются RGB-значения под
полностью прозрачными пикселями и метрики врут.

### Только декодирование (форматы входных файлов)

- Нативно браузером: JPEG, PNG, WebP, GIF, BMP, AVIF (где поддерживается).
- Через wasm: JPEG XL (всегда — нативно только в Safari, и то за флагом в остальных),
  HEIC/HEIF через `libheif-js` (айфонные снимки, без этого инструмент наполовину бесполезен).

### Отложено `[v2]`

JPEG XR, QOI, обратимая перепаковка JPEG→JXL (требует прокидывать исходные байты мимо
пиксельного пайплайна — отдельная ветка архитектуры).

### Контракты

```ts
// codecs/types.ts
type ParamSchema = ReadonlyArray<
  | { kind: 'range'; key: string; label: string; min: number; max: number; step: number; default: number }
  | { kind: 'toggle'; key: string; label: string; default: boolean }
  | { kind: 'select'; key: string; label: string; options: {value: string; label: string}[]; default: string }
>;

interface CodecAdapter {
  id: string;
  label: string;
  mime: string;
  extension: string;
  lossless: boolean | 'optional';
  params: ParamSchema;
  encode(image: ImageData, params: Record<string, unknown>, signal: AbortSignal): Promise<ArrayBuffer>;
  decode(bytes: ArrayBuffer, signal: AbortSignal): Promise<ImageData>;
}
```

**Добавление нового формата обязано сводиться к одному файлу в `codecs/` и одной строке в
реестре.** Никаких `switch` по формату где-либо ещё; контролы генерируются из `ParamSchema`
автоматически.

#### Чек-лист «добавить формат» (проверяется на приёмке этапа 2)

Полная процедура добавления нового кодека должна состоять ровно из этих шагов:

1. `npm i <пакет-кодека>`;
2. создать `src/codecs/<id>.ts`, реализующий `CodecAdapter`;
3. добавить одну строку в `registry.ts`;
4. добавить round-trip тест по общему шаблону.

Всё остальное — контролы в тулбаре, пункт в выпадающем списке, ленивая загрузка wasm,
кэширование, метрики, работа воркера — обязано подхватиться само. Ни один файл вне
`codecs/` при добавлении формата меняться не должен.

Для верификации на этапе 2 добавить фиктивный кодек `debug-blur` (размывает изображение,
«размер файла» считает синтетически) и убедиться, что он появляется в интерфейсе со своими
контролами без единой правки вне своего файла и реестра. После проверки — оставить под
флагом разработки, он же служит заглушкой для этапа 1.

Общий шаблон теста адаптера (параметризованный по всем зарегистрированным кодекам):
кодирование и декодирование тестового изображения даёт `ImageData` исходных размеров;
для lossless-режимов — побитовое совпадение; `AbortSignal` реально прерывает работу;
повторный вызов с теми же параметрами даёт байт-в-байт идентичный результат
(детерминированность нужна для кэша).

```ts
// core/image-source.ts
interface ImageSource {
  id: string;
  name: string;
  bytes: ArrayBuffer;        // исходные байты (для размера «оригинала»)
  full: ImageData;           // полный размер, sRGB 8 бит, EXIF-ориентация применена
  proxy: ImageData;          // уменьшенная копия, ≤ PROXY_MAX_PIXELS
  width: number; height: number;
}
```

## 5. Панели: заложить N, реализовать 2

`PanelState[]` — массив. В v1 длина фиксирована = 2, но **нигде в коде не должно быть
предположения о двух панелях**: ни `panels[0]/panels[1]` вместо итерации, ни имён `left/right`,
ни раскладки на два жёстких грида. Синхронизация — операция над массивом.

```ts
interface PanelState {
  id: string;
  sourceId: string;          // в режиме «Кодек» одинаков у всех панелей
  formatId: string;
  params: Record<string, unknown>;
  result: EncodeResult | null;  // { blob, bytes, decoded: ImageData, encodeMs }
  status: 'idle' | 'encoding' | 'ready' | 'error';
  error?: string;
}
```

Раскладка вычисляется из `panels.length` и ориентации: в ландшафте сначала делим по колонкам,
в портрете — по строкам. Для N=2 это ровно требуемое поведение.

## 6. Геометрия — ключевой раздел

Обозначения: `Wᵢ × Hᵢ` — размер изображения панели i в пикселях; `PW × PH` — размер панели в
CSS-пикселях; `dpr = devicePixelRatio`.

### Масштаб

Один глобальный параметр `z ∈ [0, 1]` на все панели.

```
fitᵢ = min(PW / Wᵢ, PH / Hᵢ)          // z=0: изображение целиком видно по обоим измерениям
scaleᵢ(z) = fitᵢ ^ (1 − z)             // z=1: scale = 1, попиксельно 1:1
```

Интерполяция геометрическая, не линейная — иначе вращение колеса ощущается рвано.
Если `fitᵢ > 1` (изображение мельче панели), шкала идёт в обратную сторону; логика не меняется,
клампинг не нужен.

**Режим выравнивания** (только режим «Фото», при разных размерах источников) переопределяет
`fitᵢ`:

```
'contain' (по умолчанию): fitᵢ = min(PW/Wᵢ, PH/Hᵢ)
'width':                  fitᵢ = PW / Wᵢ
'height':                 fitᵢ = PH / Hᵢ
```

При `z = 1` выравнивание игнорируется: обе панели строго 1:1.

### Позиция

Хранится **нормированная** точка `(u, v) ∈ [0,1]²` — точка изображения, находящаяся в центре
панели. Проценты вместо пикселей дают синхронизацию разноразмерных изображений бесплатно.

Видимое окно в нормированных единицах:

```
visWᵢ = PW / (Wᵢ · scaleᵢ)
visHᵢ = PH / (Hᵢ · scaleᵢ)
```

### Режимы панорамирования

**`mirror` (синхронный центр)** — у всех панелей одинаковые `(u, v)`. Один и тот же фрагмент,
показанный дважды. Режим по умолчанию.

**`continuous` (продолжение)** — панель i+1 показывает область, начинающуюся там, где
закончилась область панели i. Для горизонтальной раскладки:

```
u_{i+1} = u_i + visW_i / 2 + visW_{i+1} / 2
v_{i+1} = v_i
```

Для вертикальной — то же по `v` и `visH`. Направление берётся из текущей раскладки, не из
настройки.

### Зум с якорем под курсором

Обязательно. Без этого зум «уплывает» и инструментом невозможно пользоваться.

```
1. до изменения z: по позиции курсора внутри панели найти нормированную точку изображения (uc, vc)
2. применить новый z, пересчитать scale и vis
3. подобрать (u, v) так, чтобы (uc, vc) осталась под курсором:
   u = uc − (cursorX/PW − 0.5) · visW
   v = vc − (cursorY/PH − 0.5) · visH
4. пересчитать позиции остальных панелей согласно режиму синхронизации
5. применить клампинг
```

При зуме с клавиатуры или ползунком якорь — центр панели.

### Клампинг

Видимая область не выходит за границы изображения:
`u ∈ [visW/2, 1 − visW/2]`, аналогично `v`. Если `visW ≥ 1` — жёстко `u = 0.5` (изображение
уже целиком помещается по этой оси, центрируем).

В режиме `continuous` клампинг применяется к ведущей панели, остальные пересчитываются от неё;
допустимо, что дальние панели упрутся в край — тогда они показывают край.

## 7. Рендеринг

- Один `<canvas>` на панель. Backing store = `PW·dpr × PH·dpr`, CSS-размер = `PW × PH`.
  Без этого «1:1» будет неправдой на ретине.
- Декодированный `ImageData` **один раз** кладётся в offscreen-канвас (или `ImageBitmap`), и
  далее каждый кадр рисуется через `drawImage` с трансформацией. `putImageData` каждый кадр —
  запрещено, это убивает частоту кадров.
- `scale ≥ 1` → `imageSmoothingEnabled = false`. Смотрим настоящие пиксели, а не интерполяцию.
- `scale < 1` → многопроходный даунсемпл (последовательное деление пополам) с кэшем уровней
  мип-пирамиды. Браузерный однопроходный ресайз даёт алиасинг, и вы будете сравнивать не
  кодеки, а артефакты масштабирования.
- Общий цикл рендера на `requestAnimationFrame` с флагом «грязно»; все панели в одном кадре,
  иначе при перетаскивании они визуально разъезжаются.
- Фон панели вне изображения — тот же нейтральный серый, что и у интерфейса.

## 8. Пайплайн кодирования

```
ImageSource.full (или .proxy) → encode(params) → Blob   ← отсюда берётся размер
                                       ↓
                                    decode → ImageData  ← это рисуется на экране
```

Показывать нужно **декодированный результат**, а не оригинал: иначе сравнивать нечего.

### Прокси и производительность

- `PROXY_MAX_PIXELS = 4_000_000` (примерно 2560×1600).
- Во время перетаскивания ползунка качества кодируем прокси, debounce 200 мс. По отпусканию
  ползунка ставим в очередь кодирование полного размера.
- При `z`, требующем разрешения выше прокси, показываем полноразмерный результат; пока он не
  готов — прокси с индикатором «предпросмотр».
- Пул воркеров: `min(navigator.hardwareConcurrency − 1, 4)`. Постановка новой задачи для
  панели отменяет её предыдущую незавершённую (`AbortSignal`).
- LRU-кэш `EncodeResult` по ключу `(sourceId, formatId, hash(params), scale)`, лимит по
  суммарным пикселям, не по количеству записей.

### Память — главное ограничение

Фото 24 Мп = 96 МБ в виде `ImageData`. Оригинал + два результата + буферы внутри wasm легко
дают 400+ МБ, и мобильный Safari падает. Правила:

- Оригинал хранится в единственном экземпляре, панели ссылаются по `sourceId`.
- `ImageData` результата освобождается сразу, как только панель сменила формат или параметры.
- Мип-уровни и кэш чистятся по общему бюджету пикселей.
- При загрузке файла крупнее лимита — предупреждение и предложение работать на прокси.

## 9. Метрики

Считаются в воркере, на полном размере, между `ImageData` результата и `ImageData`
соответствующего эталона (в режиме «Фото» — эталон той же панели).

- **PSNR** — `10·log₁₀(255² / MSE)` по каналам R, G, B; альфа не учитывается. Совпадение
  байт в байт → `∞`.
- **SSIM** — окно 8×8, среднее по изображению.
- **Размер** — байты блоба, «% от оригинала», bpp.
- **Время кодирования** — мс.
- **Карта разницы** `|A − B|` с ползунком усиления. `[v2]` — как третья панель.

В подвале панели постоянно видны только: размер, % от оригинала, PSNR. Остальное — в
раскрывающейся строке. Для формата `original` метрики скрыты, размер = размер исходного файла.

Рядом с PSNR — тултип с честной оговоркой: метрика плохо коррелирует с восприятием, слегка
сдвинутый по яркости кадр получит низкий PSNR, а замыленный — высокий; окончательное решение
принимается глазами.

## 10. Интерфейс

### Раскладка

- Ориентация ландшафт → панели рядом по горизонтали; портрет → друг под другом.
  Определяется через `matchMedia('(orientation: portrait)')` плюс ручной оверрайд.
- Перетаскиваемый сплиттер, по умолчанию 50/50, двойной клик — сброс.
- Мобильный: контролы двух панелей не помещаются одновременно — переключатель
  «настройки A / настройки B» либо боттом-шит. Проектировать отдельно, не «адаптивом».

### Управление

| Действие | Результат |
|---|---|
| колесо / пинч | зум с якорем под курсором, синхронно для всех панелей |
| перетаскивание | панорама согласно режиму синхронизации |
| двойной клик | переключение fit ↔ 1:1 |
| **пробел (удержание)** | flip-тест: во всех панелях временно показывается содержимое первой |
| `+` `−` | зум шагами |
| стрелки | панорама шагами |
| `0` / `1` | вписать / 100% |

Flip-тест по пробелу — самая важная функция для оценки глазами. Мерцание при переключении в
одном и том же месте экрана глаз ловит несравнимо лучше, чем разницу двух картинок рядом.
Реализовать без задержки и без анимации перехода.

### Состояния

Спроектировать явно, не только happy path:

- пусто — приглашение перетащить файл, набор демо-изображений;
- загрузка и декодирование исходника;
- идёт кодирование (индикатор в панели, старый результат остаётся видимым, не мигаем);
- ошибка кодека — что произошло и что сделать, в панели, без модалок;
- неподдерживаемый формат файла — назвать поддерживаемые;
- слишком большой файл — предложение работать на прокси;
- COOP/COEP не настроены — предупреждение о медленной работе.

### Визуальный язык

Это измерительный прибор, а не витрина. Дисциплина важнее выразительности:

- Палитра строго нейтральная: фон около 18% серого, интерфейс в градациях серого,
  единственный акцентный цвет — только для активного состояния контролов. **Никаких цветных
  плашек, градиентов и подсветок в пределах 200 px от изображения**: цветное окружение
  сдвигает восприятие цвета и делает инструмент непригодным.
- Шрифт — один гротеск, цифры моноширинные (`font-variant-numeric: tabular-nums`), чтобы
  метрики не прыгали при обновлении.
- Хром минимальный: при зуме и перетаскивании панель контролов может притухать.
- Без анимаций переходов между состояниями изображения. Любое движение мешает заметить
  разницу между кадрами.
- Обязательный пол качества: видимый фокус с клавиатуры, `prefers-reduced-motion`,
  контрастность текста метрик не ниже AA.

## 11. Этапы

### Этап 1 — геометрия (сначала, отдельно от всего)

`core/geometry.ts` + `viewport.ts` + `render/` + минимальный UI. Кодеков нет: обе панели
показывают один и тот же загруженный файл, во второй — заглушка (например, размытие через
канвас), чтобы разница была видна.

Приёмка:
- зум колесом удерживает точку под курсором с погрешностью < 1 px на всём диапазоне;
- `z = 0` — оба изображения видны целиком; `z = 1` — оба ровно 1:1 на любом dpr;
- оба режима панорамирования работают на изображениях разных пропорций;
- изображение не выходит за границы, при `vis ≥ 1` центрируется;
- 60 fps при перетаскивании изображения 24 Мп;
- юнит-тесты на все формулы, включая граничные `fit > 1`, вырожденные размеры, ресайз окна.

**Этот этап нужно принять руками до перехода к следующему.** Если управление ощущается
неправильно — переделывать после навешивания кодеков будет дорого.

### Этап 2 — кодеки

Реестр, адаптеры, воркер-пул, кэш, прокси, генерация контролов из `ParamSchema`.

Приёмка:
- все шесть форматов кодируют и декодируют, round-trip тесты зелёные;
- `png` даёт PSNR `Infinity` — доказательство корректности пайплайна;
- переключение формата и параметров не блокирует интерфейс;
- отмена устаревших задач работает: быстрое дёрганье ползунка не копит очередь;
- HEIC-файл с айфона открывается с правильной ориентацией.

### Этап 3 — метрики и режимы

PSNR, SSIM, размеры, режим «Фото», выравнивание по ширине/высоте, flip-тест, состояния,
клавиатура.

### Этап 4 `[v2]`

Батч: сетка «формат × качество» с миниатюрами, размером и PSNR под каждой, плюс график
размер↔PSNR по всем форматам (видно, чья кривая ниже). Клик по ячейке открывает её в панели
сравнения. Считать на прокси.

Также в v2: больше двух панелей, карта разницы третьей панелью, режим «шторка» с наложением
и подвижной границей, сохранение сжатого файла, ссылка с настройками.

## 12. Тесты

- Юнит: вся `core/geometry.ts` (главный приоритет), `metrics.ts` на синтетических данных с

## 13. Деплой

Приложение полностью статическое: сборка Vite кладётся на любой статический хостинг. Единственное
требование, которое отсекает часть площадок, — **возможность задавать HTTP-заголовки**
(COOP/COEP, см. раздел 2).

Целевая площадка — **Cloudflare Pages**, выкладка из CI по релизу (раздел 14). Встроенную
Git-интеграцию Pages не подключаем. В корень публикуемой директории положить файл
`_headers`:

```
/*
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Embedder-Policy: require-corp

/assets/*
  Cache-Control: public, max-age=31536000, immutable
```

Вторая секция важна: wasm-бинарники кодеков суммарно весят десятки мегабайт, и без
долгого кэша каждый заход будет их перекачивать. Vite проставляет хеши в имена файлов, так
что `immutable` безопасен.

Проверка после деплоя: в консоли `self.crossOriginIsolated === true`. Если `false` —
многопоточность и SIMD отключены, AVIF и JXL работают в разы медленнее.

Настроить `vite.config.ts` так, чтобы dev-сервер отдавал те же два заголовка, иначе локальная
разработка будет вести себя иначе, чем прод.

Добавить в README раздел с эквивалентной конфигурацией для Netlify (тот же `_headers`),
Vercel (`vercel.json` → `headers`) и Firebase (`firebase.json` → `hosting.headers`).

**GitHub Pages не подходит** без обходного пути: произвольные заголовки там не задаются.
Если площадка всё же GitHub Pages — подключить `coi-serviceworker`, который подставляет
заголовки на клиенте, и учесть, что COEP ломает загрузку любых сторонних ресурсов без CORS.
Отразить деградацию в интерфейсе: при `crossOriginIsolated === false` показывать
предупреждение о медленном кодировании.

## 14. CI/CD

### Принцип

Прод обновляется при попадании изменений в `main`. Разработка ведётся в ветках, влитие в
`main` через PR — это и есть акт выкладки.

Встроенную Git-интеграцию Cloudflare Pages **не подключаем**, хотя она умеет ровно это.
Причина одна: при её использовании деплой происходит на стороне Cloudflare, и smoke-тест
(проверку заголовков, см. ниже) поставить некуда. Вместо неё — прямая загрузка из GitHub
Actions через `wrangler pages deploy`. Побочная выгода: сборка идёт в Actions и не расходует
лимит в 500 сборок Pages.

Ветки: `main` — то, что на проде, прямые пуши запрещены (branch protection). Работа —
в `feature/*`, влитие через PR с зелёным CI и проверенным превью.

### Три воркфлоу

**`.github/workflows/ci.yml`** — на каждый push в не-`main` ветку и на pull request:

```
typecheck (tsc --noEmit) → lint → unit-тесты → build
```

Деплоя нет. `concurrency` с `cancel-in-progress: true`, чтобы новый пуш отменял предыдущий
прогон. Кэш npm через `actions/setup-node`. Права `contents: read`.

**`.github/workflows/preview.yml`** — на pull request:

Тот же прогон плюс `wrangler pages deploy --branch=pr-<номер>`, ссылка на превью постится
комментарием в PR. Нужно, чтобы визуальные изменения можно было посмотреть до влития.

**`.github/workflows/deploy.yml`** — на `push` в `main`:

```
проверки → build → wrangler pages deploy --branch=main → smoke-тест → при падении откат
```

Плюс `workflow_dispatch` для ручного передеплоя без нового коммита.

`[v2]` Если однажды понадобится отделить «влито» от «выложено» — сменить триггер на
`release: published` и добавить в регламент шаг с созданием GitHub Release. Всё остальное в
воркфлоу останется прежним, поэтому закладывать это заранее не нужно.

### Секреты и доступы

- `CLOUDFLARE_API_TOKEN` — токен с единственным правом «Cloudflare Pages: Edit».
  Не использовать глобальный ключ аккаунта.
- `CLOUDFLARE_ACCOUNT_ID`.
- Оба — в GitHub Secrets, в Environment `production`, привязанном к `deploy.yml`.

### Версия в сборке

Версия прокидывается в бандл через `define` в `vite.config.ts`: `__BUILD_SHA__` (короткий хеш
коммита) и `__BUILD_DATE__`. Отображается мелко в углу интерфейса и выводится в консоль при
старте. Без этого невозможно понять, какую сборку видел человек, приславший баг.

### Smoke-тест после деплоя

Обязательный шаг в `deploy.yml`: headless-браузер (Playwright) открывает задеплоенный URL и
проверяет:

1. `self.crossOriginIsolated === true` — заголовки COOP/COEP доехали;
2. загрузка тестового изображения из фикстур проходит;
3. кодирование в WebP и в JXL завершается, PSNR для `png` равен `Infinity`.

Первый пункт — главный. Именно он ловит самую вероятную поломку прода: `_headers` не попал в
publish-директорию, и всё внешне работает, но кодирование стало в разы медленнее. Молчаливую
деградацию иначе никто не заметит.

При падении smoke-теста — автоматический откат на предыдущий успешный деплой
(`wrangler pages deployment`), падение воркфлоу и уведомление. Команду для ручного отката
продублировать в README.

### Что не коммитим

Wasm-бинарники кодеков приходят из npm и в репозиторий не попадают. В `.gitignore`:
`dist/`, `node_modules/`, `.wrangler/`. Тестовые изображения-фикстуры держать маленькими
(до ~200 КБ каждое), иначе репозиторий распухнет.
